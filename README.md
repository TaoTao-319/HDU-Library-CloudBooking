# HDU Library CloudBooking · 杭电图书馆四楼自动预约

每天 20:00 学校放开座位时，由**本机 19:50 计划任务**登录、按等级优先级抢四楼座位；
云端（GitHub Actions）只保留手动 `workflow_dispatch` 兜底，不再自动触发。
本仓库是 `TaoTao-319/HDU-Library-AutoBook` 的独立重写版本：座位优先级与时段规则沿用，
登录方式与调度方式整体替换。本机脚本目录 `26 10 19 图书馆脚本` 未做任何改动。

## 为什么原来的云端仓库无法自动预约

排查了原仓库的运行记录，云端的失败不在"定时"这一环，而是两层问题叠加：

1. **自动入口被删掉了。** 原仓库当前的 `main.yml` 只有 `workflow_dispatch`（手动）触发，
   自动定时被注释掉，所以云端根本没有自动预约的入口，只有手动能跑。
2. **浏览器登录在云端会超时。** 原脚本用 Selenium 打开无头 Chrome 走统一身份认证。
   原仓库唯一一次真正由 `schedule` 触发的运行（2026-10-21 16:00:40 北京时间，run 39566063473）
   就死在这里：

   ```
   16:01:10 学校登录表单已就绪
   16:01:10 已提交学校登录表单，等待返回图书馆
   16:02:10 ERROR 登录超时阶段：等待认证完成并返回图书馆；页面：sso.hdu.edu.cn/login
   16:02:10 ERROR 浏览器网络错误：['net::ERR_ABORTED']
   ```

   同一天 10:59 前后的诊断记录过"零次 schedule 运行"，那是新注册的 cron 需要数小时才生效；
   cron 真正开始投递后，暴露出来的第一个真实故障就是上面的浏览器登录超时。

## 这个仓库做了什么

### 1. 用纯 HTTP 完成统一身份认证，不再启动浏览器

抓取并复现了学校 CAS 客户端的提交协议：

- `GET /User/Index/hduCASLogin?forward=%2FSeat%2FIndex%2Findex` → 跳转 `sso.hdu.edu.cn/login`
- 从登录页读取隐藏字段 `login-croypto`（16 字节 AES 密钥，base64）与 `login-page-flowkey`（execution）
- 密码按站点 JS 的算法加密：`base64(AES-128-ECB(PKCS7(password), base64decode(croypto)))`
- `POST https://sso.hdu.edu.cn/login`，表单字段
  `username / type / _eventId / geolocation / execution / captcha_code / croypto / password / captcha_payload`
- 跟随 302 回到图书馆，拿到 `PHPSESSID` 后复用同一个 `requests.Session` 下单

效果：整个 Job 从原来的 60~90 秒（装 Chrome + 启动 + 登录）降到 **22 秒**，
登录本身 3~7 秒，且没有浏览器版本、驱动、页面渲染这类不稳定因素。
`selenium` 已从依赖中移除。

### 2. 定时：本机 19:50 计划任务（云端 schedule 已关闭）

2026-10-24 起不再指望云端自动抢座：

- GitHub 原生 `schedule` 对本仓库长期零投递（多轮探测零事件），云端 Job 从 19:20
  启动还要等 40 分钟才提交，既慢又不确定；
- 同一账号再叠一个云端 Job，只会在整点限流之外多一层竞争，**拖慢**本机抢座。

所以现在：

| 通道 | 状态 | 说明 |
|---|---|---|
| 本机 `HDU-Library-Daily` | **启用** | 每天 19:50 启动，登录+备好候选，程序内部等到 20:00:00.000 提交 |
| 本机 `HDU-Cloud-Trigger-1920` | **已禁用** | 原来 19:20 用 gh 触发云端 |
| GitHub `schedule` | **已删除** | `main.yml` 只剩 `workflow_dispatch` 手动兜底 |

程序仍然保留 20:15 cutoff 和 late-start 分支：20:00 之后才启动也会立即提交，
只要还在当日窗口内就继续按等级换座重试。

### 3. 抢座仍是"等级优先 + 等级内随机"

四楼后台 ID = 页面座位号 + 62564，1–332 号对应 62565–62896。

| 等级 | 四楼座位号 | 后台 ID 区间（含两端） | 数量 |
|---|---|---|---|
| 特等座 | 17–58 | 62581–62622 | 42 |
| 一等座 | 307–332 | 62871–62896 | 26 |
| 二等座 | 1–16、59–306 | 62565–62580、62623–62870 | 264 |

- 整点先直接提交一个随机特等座，避免座位图查询拖慢第一个请求；
- 整点被立即限流（2026-10-23 实测 20:00:00.02 就返回"请求太频繁"）时，在本轮预算内
  按 **1 / 2 / 3 秒**退避连续重试同一座位，不再弃轮等到 20:00:25；
- 提交读超时压到 **4 秒**，4 秒没回音立刻进下一枪；放号前 90 秒内不再拉
  `myBookingList`（高峰期这一页要 2–6 秒），整点前后只做"备座 + 提交"；
- 被占用后才查实时空位，按特等座 → 一等座 → 二等座继续，等级内部重新随机，绝不跨级打乱；
- 一天最多五轮：20:00:00、20:00:25、20:01:00、20:02:00、20:04:00；
- 成功、四楼确认无位、或已有覆盖订单即提前结束；
- 整点后 8 秒内遇到"超出可预约座位时间范围"最多重试 4 次（0.15 / 0.35 / 0.75 / 1.5 秒）。

### 4. 每周时段

按**预约日期**读取 `user_config.yml`（例如周三晚预约的是周五），日期取"今天 + 2 天"：

| 预约日期 | 启用 | 开始 | 持续 |
|---|---|---|---|
| 周一 | true | 15:00 | 7 小时 |
| 周二 | true | 16:00 | 6 小时 |
| 周三 | true | 10:00 | 12 小时 |
| 周四 | true | 15:00 | 7 小时 |
| 周五 | true | 13:00 | 9 小时 |
| 周六 | true | 10:00 | 12 小时 |
| 周日 | true | 10:00 | 12 小时 |

## 部署与运行

本机（主通道，已经装好）：

```powershell
.\Save-Credential.ps1                 # 一次性：DPAPI 保存学号/密码到 .local\credentials.xml
.\Install-Schedule.ps1                # 注册 HDU-Library-Daily，每天 19:50 启动 --daily
.\Install-Schedule.ps1 -Remove        # 需要时卸载
```

日志在 `logs\YYYY-MM-DD.log`，订单快照在 `.local\booking-*.json`。

手动跑一次：

```powershell
.\.venv\Scripts\python.exe main.py --check --start 15 --hours 7   # 只读检查
.\.venv\Scripts\python.exe main.py --daily                        # 五轮计划（会等到 20:00）
.\.venv\Scripts\python.exe -m unittest test_main test_seat_plan    # 离线回归
```

云端（只作手动兜底）：`Actions → HDU Auto Book → Run workflow`，
`mode = check` 只读、`mode = book` 真实预约；不会自动触发。
